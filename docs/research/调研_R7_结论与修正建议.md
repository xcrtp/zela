## 1. 四个问题

| # | 问题 | 答案 | 落点 |
|---|---|---|---|
| 1 | 要哪些 `Semantic`？ | `Position` / `Uv` / `ShadingNormal` / `Attrib0` / `Attrib1` / `Attrib2`，并预留 `Joints0` / `Weights0` | `ze-vertex/src/semantic.rs` |
| 2 | 需求声明放哪？ | 类型 `ShaderRequirements { semantics: Vec<Semantic> }` 放 **IR**（`PipelineDesc` 新字段）；"哪个入口要哪些语义"的**数据**放后端 `wgpu_3d.rs` | `ze-render-ir/src/pipeline.rs` + `zela-render-backends/src/wgpu_3d.rs` |
| 3 | 默认值表放哪？ | `Semantic::default_value()`，与 R2 正向清单同源（`Uv → (0,0)`、`ShadingNormal → (0,0,1)`） | `ze-vertex/src/semantic.rs` |
| 4 | 调和规则放哪？ | `reconcile(required, provided) -> ReconcilePlan`，纯函数；**调用点在写出端**（生产端打包前），不在后端 | `ze-vertex/src/reconcile.rs`，由 `zela-render/src/vertex_record.rs` 调用 |

## 2. 六项结论摘要

| 项 | 结论 |
|---|---|
| R1 | 11 处调用点 / 9 个位置：1 定义、1 写出、2 消费、7 断言。**结构性发现：布局在录制期现场构造，不随 draw 携带** —— 这是任何多布局方案的前置条件 |
| R2 | 正向默认值 6 条（`uv→(0,0)`、`normal→(0,0,1)`、整几何缺 UV 走 `fallback_uvs` 等）。**反向：wgpu 不支持常量顶点属性**，替代方案只能是"写出端补齐" |
| R3 | `U8x4Norm`：`size()=4`、`alignment()=4`（沿用）、`to_wgpu_format → Unorm8x4`。**本批不加**（无消费者），加时是 3 处穷尽 match 各补一行 |
| R4 | 语义枚举化但**不替换** `semantic: &'static str`；与 2D `AttribSemantic` **并存不合并** |
| R5 | `VertexLayout` **不进 payload** ⇒ 加字段不必 bump `LIBRARY_VERSION`、不必重录 36 条像素 / 22 件结构 |
| R6 | 三拓扑可用不同布局，但"只缩布局"会**管线创建失败**：必须同时给 shader 加 `vs_line` 并让布局随 draw 携带 |

## 3. 对原实施计划「阶段 1」的修正建议

原计划写的是：

```
小–中 · 像素 36 条不变 + standard_3d() 布局快照逐字段不变
```

逐条核对后有 **5 处需要修正**、**1 处需补进范围**：

### 修正 1（补范围）：阶段 1 必须包含"布局随 draw 携带"

- 原计划只提"语义体系 + 调和规则"，默认布局仍可由后端现场取。
- 调研发现：`Skeleton` / `PreparedDraw3D` / `PipelineKey` 都不含 `VertexLayout`，后端在 [wgpu_3d.rs:1318](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render-backends/src/wgpu_3d.rs#L1318) 每次现调 `standard_3d()`。
- 后果：阶段 1 即使产出了"第二种布局"，也没有任何 draw 能声明它，机制等于空转。
- **建议**：把"布局随 draw 携带"列进阶段 1（该改动不改像素、可独立验收），否则阶段 1 的产出无法被消费。

### 修正 2（改口径）："布局快照逐字段不变"只对 `standard_3d()` 本身成立

- 这句话在"只加构造器 / 枚举 / 默认值表"时成立。
- 但一旦引入第二种 3D 布局（骨骼 / 缩窄的 Lines），`PipelineKey` 的哈希与进程内 pipeline 数量都会变 —— 这不是像素问题，也不是 payload 问题（R5），但会让"快照不变"这句话读起来像承诺了更多。
- **建议**改写为：`standard_3d()` 逐字段不变（[layout.rs:443](file:///d:/Users/xcdh/Desktop/xc/zela/crates/kernel/ze-vertex/src/layout.rs#L443) 与 [wgpu_3d.rs:1725](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render-backends/src/wgpu_3d.rs#L1725) 两条断言仍绿）；新增布局各有自己的断言。

### 修正 3（删顾虑）：不需要 bump `LIBRARY_VERSION`、不需要重录基线

- 原计划把"要不要搭 bump 的顺风车"当风险项。
- R5 证据链完整：payload 只装 `SceneScript` 的规范 JSON（[zela-scene-bundle/src/lib.rs:11-19](file:///d:/Users/xcdh/Desktop/xc/zela/crates/scene/zela-scene-bundle/src/lib.rs#L11-L19)），`VertexLayout` 在 scene 侧无引用，serde 只被测试驱动。
- **建议**：从阶段 1 里删掉这项风险与配套的"重录 manifest"动作。

### 修正 4（改方案）：反向调和的实现位置是写出端，不是后端

- 原计划把"反向调和"写成待定机制。
- R2 定案：wgpu 30 不支持常量顶点属性（`InputError::Missing` 直接失败），专用兜底 buffer 只在 `instance_count == 1` 时成立。
- **建议**：`reconcile` 的调用点定在 `zela-render/src/vertex_record.rs` 的 `mesh_vertex_buffer` / `line_vertex_buffer`；后端只做"契约 → wgpu"翻译，不参与补齐。附加一条必须保留的行为：默认值表查不到时**显式报错**，不许猜值。

### 修正 5（降预期）：Lines 不是"最便宜的验证靶"

- 原计划设想用 Lines 缩窄布局来"用最小成本验证机制"。
- R6 核算：省下的字节是每条线 40 字节（线框立方体 8 顶点 ⇒ 160 字节），可忽略；而代价是一次 shader 改动（新增 `vs_line`）+ 一次数据结构改动 + 入口点从常量改成查表。
- **建议**：阶段 1 的机制验证靶换成 **CPU 侧的"写出端补齐"**（零 shader 改动、可用纯 CPU 单测断言字节）；Lines 缩窄移到下一批，作为"多布局确实能跑通"的第二个靶。

### 修正 6（改取舍）：U8 归一化不阻塞骨骼

- 原计划把"需不需要 U8 归一化"当成"决定骨骼能否落地"。
- R3 结论：不加也能落地（用 `F32x4` 承载索引与权重），代价是 4 倍带宽（每顶点 32 B vs 8 B）。
- **建议**：阶段 1 不引入 `U8x4Norm`；骨骼批开始时再按 R3 §2 的确定取值一次加上。

## 5. 建议的实施顺序（阶段 1 内部）

1. `ze-vertex`：`semantic.rs`（枚举 + 默认值）、`reconcile.rs`（纯函数）—— 纯数据、可全部用单测验收。
2. `ze-render-ir`：`ShaderRequirements` + `PipelineDesc.requirements`；后端补 `vs_requirements` 常量表。
3. `zela-render`：`mesh_vertex_buffer` / `line_vertex_buffer` 调 `reconcile`，替换现有手工兜底（**输出字节必须逐位不变**，这是本阶段最强的验收断言）。
4. 后端：`Skeleton` / `PreparedDraw3D` / `PipelineKey` 携带布局，删掉 `wgpu_3d.rs:1318` 的现场构造。
5. 收尾：`cargo verify --step hashes` + `--step structure`，与第 1 步之前的读数比对。

> 第 3 步是关键：把"手工兜底"换成"查表补齐"时，字节必须逐位相同 —— 这条断言同时验证了 R2 的正向清单和 R4 的默认值表，比任何抽象描述都直接。
