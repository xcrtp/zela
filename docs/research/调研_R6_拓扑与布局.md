# 调研 R6 · 拓扑与布局的关系

> 现状：`Triangles` / `Lines` / `Points` 三种拓扑共用 `standard_3d()`（stride 32，带 uv 与 normal）
> 性质：只读调研，不改代码 / shader

## 1. 结论

**能用不同布局，但"只缩布局"做不到 —— 必须同时给 shader 加一个只读 `position` 的顶点入口，并让布局随 draw 携带。**
本批不改 shader ⇒ 结论是「机制可行、需三件配套改动、留到下一批」。

## 2. 三个前置事实

**① 布局在录制期现场构造，不随 draw 携带。**
见 R1 §3：[wgpu_3d.rs:1318](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render-backends/src/wgpu_3d.rs#L1318) 每个 draw 都现调 `standard_3d()`。⇒ 只要出现第二种布局，后端无从知道这条 draw 属于哪一种。

**② shader 只有一个顶点入口，且读三个 location。**
[cube.wgsl:83-87](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render-backends/shaders/cube.wgsl#L83-L87)：

```wgsl
fn vs_main(
    @location(0) pos: vec3<f32>,
    @location(1) uv: vec2<f32>,
    @location(2) normal: vec3<f32>,
)
```

管线创建处固定 `entry_point: Some("vs_main")`（[wgpu_3d.rs:1361](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render-backends/src/wgpu_3d.rs#L1361)）。

**③ wgpu 不允许"shader 要的 location 但布局不给"。**
详见 R2 §2：`wgpu-core-30.0.1/src/validation.rs:1554-1560` `InputError::Missing`。

⇒ 如果只把 Lines 的布局缩成 position-only，**管线创建会直接失败**（明确的报错，不是静默降级）。这不是"能不能"的性能问题，是"配不配套"的问题。

## 3. 每种拓扑是否需要 uv / normal

| 拓扑 | 现有生产者 | 实际消费 uv？ | 实际消费 normal？ |
|---|---|---|---|
| `Triangles` | `solid_cube`、`parametric_surface`、2D 派生片 | 是（纹理 decal + PBR 的 uv 导数 TBN） | 是（Lambert / PBR 光照） |
| `Lines` | `LineDraw`（[wgpu_3d.rs:1153-1223](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render-backends/src/wgpu_3d.rs#L1153-L1223)，2 顶点）、`wireframe_cube`（[cube.rs:27-39](file:///d:/Users/xcdh/Desktop/xc/zela/crates/scene/ze-scene-core/src/mesh_primitives/cube.rs#L27-L39)） | **否**。绑定的永远是 1×1 透明黑兜底纹理（`DEFAULT_TEXTURE_ID`，[:1217-1219](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render-backends/src/wgpu_3d.rs#L1217-L1219)）⇒ `tex = (0,0,0,0)` ⇒ `color_lambert` 里 `albedo = color * lit`，uv 不进入结果 | **名义上要**（`lit` 靠它），但取值恒为 `(0,0,1)`（写出端兜底）⇒ 与"顶点不动、shader 里写常量 `(0,0,1)`"逐位等价 |
| `Points` | **无生产者**；后端 [:1305-1309](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render-backends/src/wgpu_3d.rs#L1305-L1309) 显式 panic | — | — |

> `Points` 没有生产者，讨论它的布局没有收益；本调研建议**不动**。

## 4. 建议布局与 stride / offset

| 拓扑 | 建议布局 | offset | stride | 相对现状 |
|---|---|---|---|---|
| `Triangles` | 不变：`position F32x3` + `uv F32x2` + `shading_normal F32x3` | 0 / 12 / 20 | 32 | 基准 |
| `Lines` | `position F32x3` | 0 | **12** | −20 字节/顶点（−62.5%） |
| `Points`（若将来要） | `position F32x3` | 0 | 12 | 同 Lines |

手算核对（`compute_layout`，对齐恒为 4）：

```text
Lines:  position F32x3 @0，cursor = 0 + 12 = 12  ⇒ stride 12（12 是 4 的倍数，无填充）
Triangles: 0 + 12 = 12 → uv F32x2 @12，cursor 20 → normal F32x3 @20，cursor 32 ⇒ stride 32
```

## 5. 为什么既有像素可以不变（论证，不是断言）

要把 Lines 缩成 stride 12，shader 需要一个 `vs_line`：

```wgsl
fn vs_line(@location(0) pos: vec3<f32>) -> VertexOutput {
    var out: VertexOutput;
    out.position = u.mvp * vec4<f32>(pos, 1.0);
    out.color = u.color;
    out.uv = vec2<f32>(0.0, 0.0);      // 等价于现在的兜底值
    out.normal = vec3<f32>(0.0, 0.0, 1.0);  // 等价于现在写出端的兜底值
    out.world_pos = (u.model * vec4<f32>(pos, 1.0)).xyz;
    return out;
}
```

逐项对齐现状：

1. `uv`：现状写出端对 LineDraw 直接写 `(0,0)`（[vertex_record.rs:265-268](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render/src/vertex_record.rs#L265-L268)）；对 `wireframe_cube` 走 `fallback_uvs`（包围盒投影），但该路径**不消费** uv（无纹理 ⇒ `tex = 0`）。⇒ 常量 `(0,0)` 与现状像素等价。
2. `normal`：现状 `(0,0,1)`（`Vec3::Z` 兜底）；`normalize((0,0,1)) = (0,0,1)`，`lit` 与任何光源集合下都与"顶点携带 `(0,0,1)`"相同。⇒ 常量等价。
3. `world_pos`：只依赖 `pos` 与 `model`，不受影响。
4. Z-order 的 `epsilon` 是 CPU 侧平移（[wgpu_3d.rs:1108-1113](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render-backends/src/wgpu_3d.rs#L1108-L1113)），不读顶点法线 ⇒ 不受影响。

**唯一风险点**：若某条 Lines draw 走了 `ShaderVariant::Pbr`，`color_pbr` 用 uv 导数构造屏幕空间 TBN（[cube.wgsl:167-175](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render-backends/shaders/cube.wgsl#L167-L175)），常量 uv 会让导数恒 0 ⇒ `det = 0` ⇒ NaN。当前作品里 LineDraw 固定 Lambert（[:1211](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render-backends/src/wgpu_3d.rs#L1211)），`wireframe_cube` 走材质默认变体（Lambert），故既有基线不受影响；但机制上必须**禁止 Lines 用 Pbr**，或给 `vs_line` 一并提供非退化 uv。

## 6. 收益的诚实评估

| 收益 | 量级 |
|---|---|
| 字节 | 每条线 −40 字节；线框立方体 8 顶点 ⇒ −160 字节。**可忽略** |
| 机制验证 | **这是主要收益**：第一次证明"同一后端、同一 shader 模块下，不同拓扑走不同顶点布局，且像素不变" |
| 前置成本 | 三件事：布局随 draw 携带、`vs_line` 入口、按拓扑选入口（`entry_point` 从常量改成查表） |

⇒ 计划里"用 Lines 验证机制"的设想成立，但**它不是零成本的验证靶**：省下的字节微不足道，付出的是一次 shader 改动 + 一次数据结构改动。**如果目标是"最便宜地验证机制"，更好的验证靶是 R2 的"写出端补齐"（纯 CPU，零 shader 改动）。**

## 7. 实施顺序建议（若将来要做）

1. 先让 `Skeleton` / `PreparedDraw3D` / `PipelineKey` 携带 `VertexLayout`（把 [:1318](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render-backends/src/wgpu_3d.rs#L1318) 的现场构造换成"从 draw 里读"）—— 这一步不改像素，可独立验收。
2. 再加 `standard_3d_lines()` 与 `vs_line`，按拓扑选入口。
3. 收尾跑 `cargo verify --step hashes` + `--step structure`，读数必须与改动前一致。
