# 调研 R4 · 语义词汇表与需求声明的落点

> 问题：语义要不要枚举化？与 2D 的 `AttribSemantic` 合并还是并存？需求声明 / 默认值表 / 调和规则各放哪？
> 性质：只读调研，不改代码
> 本文内容并入 [调研_R7_结论与修正建议.md](file:///d:/Users/xcdh/Desktop/xc/zela/docs/research/调研_R7_结论与修正建议.md)

## 1. 现状：两个同名不同物的"语义"

| 概念 | 位置 | 形态 | 覆盖面 |
|---|---|---|---|
| `AttribSemantic` | [aa.rs:30-49](file:///d:/Users/xcdh/Desktop/xc/zela/crates/kernel/ze-vertex/src/aa.rs#L30-L49) | 枚举，参与 serde | **2D AA 模型内**的槽角色：`Undefined/Normal/Uv/SdfGradient/Coverage/Side/Advance/SdfDistance` |
| `VertexAttrib.semantic` | [layout.rs:92](file:///d:/Users/xcdh/Desktop/xc/zela/crates/kernel/ze-vertex/src/layout.rs#L92) | `&'static str`，参与 serde，反序列化宽松（`Box::leak`） | **全局面**的属性身份：`position/uv/shading_normal/attrib0/attrib1/attrib2` |

关键区分：`AttribSemantic::Normal` 是"**2D 边法线**在该模型里扮演什么角色"，`shading_normal` 是"**3D 着色法线**这个属性本身"。两者不可互换 —— 这正是 D3 把 3D 法线命名成 `shading_normal` 而不是 `normal` 的原因。

## 2. 四个落点（结论）

### 2.1 语义清单：要哪些 `Semantic`

**落点**：`crates/kernel/ze-vertex/src/semantic.rs`（新文件，纯数据，无新依赖）

```rust
pub enum Semantic {
    Position,
    Uv,
    ShadingNormal,
    Attrib0,        // 2D 通用槽
    Attrib1,
    Attrib2,
    Joints0,        // 预留：骨骼索引
    Weights0,       // 预留：骨骼权重
}

impl Semantic {
    pub const fn as_str(self) -> &'static str;      // 与现有词汇表逐字一致
    pub fn of(name: &str) -> Option<Self>;          // 字符串 → 枚举
    pub const fn default_value(self) -> Option<[f32; 4]>;  // 默认值表（见 2.3）
}
```

**要不要把 `VertexAttrib.semantic` 从 `&'static str` 改成枚举？不要。**

理由：
1. 该字段**参与 serde**，且反序列化刻意宽松（[layout.rs:110-138](file:///d:/Users/xcdh/Desktop/xc/zela/crates/kernel/ze-vertex/src/layout.rs#L110-L138)）—— 实例化 buffer 的语义是**宿主自定义**的（`instance_offset`、`instance_color`…）。改成枚举就必须带 `Custom(&'static str)` 变体，`Box::leak` 逻辑照旧，收益为零、改动面变大。
2. 现有 `VOCABULARY` 数组（[layout.rs:105-107](file:///d:/Users/xcdh/Desktop/xc/zela/crates/kernel/ze-vertex/src/layout.rs#L105-L107)）可以改成"由 `Semantic::ALL` 派生"，词汇表就只剩一份定义，不必动字段类型。

⇒ 形态是 **"字符串字段 + 枚举视图"**：枚举给编译期检查与新逻辑（需求声明 / 默认值 / 调和）用，字符串仍是序列化与宿主扩展的口径。

### 2.2 与 2D 的 `AttribSemantic`：**并存，不合并**

| 理由 | 说明 |
|---|---|
| 语义层次不同 | `AttribSemantic` 是"模型内的相对角色"（`AaModel::None` 下三个槽全是 `Undefined`）；`Semantic` 是"属性的绝对身份" |
| 合并会让 `Undefined` 表达不出来 | 合并后"这个槽在该模型下不可读"这件事只能靠 `Option` 临时表达，反而更绕 |
| 序列化面不同 | `AttribSemantic` 已进 `AaSlotSemantics`（2D 契约的一部分），改它会牵动 2D 的映射表与三轮穷举测试（[aa.rs:106-177](file:///d:/Users/xcdh/Desktop/xc/zela/crates/kernel/ze-vertex/src/aa.rs#L106-L177)） |
| 现有分层是刻意的 | 模块头写明"3D 走硬件 MSAA，不参与 2D AA 契约"（[layout.rs:8-9](file:///d:/Users/xcdh/Desktop/xc/zela/crates/kernel/ze-vertex/src/layout.rs#L8-L9)） |

⇒ 两者**并存**，并在 `semantic.rs` 里写一行对照注释（`AttribSemantic::Normal` = 2D 边法线 ≠ `Semantic::ShadingNormal`），防止后来者误合并。

### 2.3 默认值表：`ze-vertex/src/semantic.rs`

**落点**：`crates/kernel/ze-vertex/src/semantic.rs`，挂在 `Semantic::default_value()` 上。

| 语义 | 默认值 | 来源（与 R2 正向清单同源） |
|---|---|---|
| `Position` | `None`（无默认，必须提供） | 位置无法臆造 |
| `Uv` | `Some([0.0, 0.0, 0.0, 0.0])` | [vertex_record.rs:191](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render/src/vertex_record.rs#L191) |
| `ShadingNormal` | `Some([0.0, 0.0, 1.0, 0.0])` | [vertex_record.rs:192](file:///d:/Users/xcdh/Desktop/xc/zela/crates/render/zela-render/src/vertex_record.rs#L192)（`lit = 1` 的设计取值，不得改） |
| `Attrib0` | 沿用 2D 语义：`[0.0, 0.0, 0.0, 0.0]` | 2D 三角化器必然产齐，此值只用于"跨模型误用"的显式补齐 |
| `Attrib1` / `Attrib2` | `[0.0; 4]` | 同上 |
| `Joints0` | `Some([0.0; 4])` | 全部指向骨骼 0 |
| `Weights0` | `Some([0.0, 0.0, 0.0, 0.0])` | **全零权重 = 无骨骼影响**（不能用 `[1,0,0,0]`，那会把所有顶点绑到骨骼 0） |

放这里的理由：纯常量、无依赖、`ze-vertex` 已是"格式契约"层（`Cargo.toml` 只依赖 `serde` + `thiserror`，[Cargo.toml:14-16](file:///d:/Users/xcdh/Desktop/xc/zela/crates/kernel/ze-vertex/Cargo.toml#L14-L16)）；生产端（`zela-render`）与 IR 都能直接用。

### 2.4 需求声明：类型在 IR，数据在后端

**类型落点**：`crates/kernel/ze-render-ir/src/pipeline.rs`，作为 `PipelineDesc` 的新字段。

```rust
pub struct ShaderRequirements {
    /// 顶点入口要求提供的语义，顺序 = shader location 顺序。
    pub semantics: Vec<ze_vertex::Semantic>,
}
```

放在 IR 的理由：`PipelineDesc` 就是"管线意图声明"（[pipeline.rs:26-42](file:///d:/Users/xcdh/Desktop/xc/zela/crates/kernel/ze-render-ir/src/pipeline.rs#L26-L42)），且 `ze-render-ir` 已依赖 `ze-vertex`（[ze-render-ir/Cargo.toml:22](file:///d:/Users/xcdh/Desktop/xc/zela/crates/kernel/ze-render-ir/Cargo.toml#L22)），依赖方向不需要新增边。

**数据落点**：`crates/render/zela-render-backends/src/wgpu_3d.rs`，一张常量表：

```rust
fn vs_requirements(entry: &'static str) -> ShaderRequirements { /* "vs_main" => pos/uv/normal */ }
```

理由："哪个顶点入口读哪些 location"是 **shader 源文件的事实**，而 shader 属于后端 crate。IR 只规定契约形状，不复制这份事实（复制 = 第二份定义 = 必然漂移）。

### 2.5 调和规则：`ze-vertex/src/reconcile.rs`

```rust
pub struct ReconcilePlan {
    /// 补齐后的布局（属性顺序 = 需求顺序）
    pub layout: VertexLayout,
    /// 每个补齐槽要写入的常量（生产端据此在交错数组里插值）
    pub padding: Vec<Padding>,
}

pub struct Padding {
    pub semantic: Semantic,
    pub ty: AttribType,
    pub value: [f32; 4],
}

pub enum ReconcileError {
    /// 需求里有该语义，但默认值表里没有（不许猜值）
    NoDefault(Semantic),
    /// 需求的顺序与提供的布局无法对齐
    OrderMismatch { required: Semantic, provided: &'static str },
}

pub fn reconcile(
    required: &[Semantic],
    provided: &VertexLayout,
) -> Result<ReconcilePlan, ReconcileError>;
```

放在 `ze-vertex` 的理由：函数的输入输出全是 `ze-vertex` 自己的类型（`Semantic` / `VertexLayout` / `AttribType`），不碰 wgpu、不碰 IR；调用方是**生产端**（`zela-render::vertex_record`），不是后端（见 R2 §2.3：反向调和的可行做法是写出端补齐）。
