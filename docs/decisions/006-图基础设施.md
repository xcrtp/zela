# 006 · 图基础设施

> **状态**：已采纳
> **锚点**：GAPS AN-02 · AO-05 · `ze_graph_core::topology::Topology` · `ze_graph_core::sort::topo_sort`
> **被谁取代**：—

## 决策

图算法独立成 `ze-graph-core`，并遵守三条强制约束：

- 零 crate 依赖（只依赖标准库的容器与既有内核类型），保证任何层都能依赖它而不引入反向边。
- 输出一律升序：用 `BTree*` 而非 `HashMap`，同一张图两次输出逐位相同。
- 算法只依赖最小 `Topology { nodes(), successors() }`：算法不该知道什么是 Node、什么是 ObjectId。

配套两条：遍历器抽象统一为「前序 `enter` 可剪枝 + 后序 `leave`」与 `map_children`；环检测返回**完整环路径**而不是「有环」这个布尔。

## 理由

图算法的复用面比想象中宽：表达式 DAG、时钟父子链、场景父子层级、曲面引用、Pod 装配依赖，都是同一类问题。过去每处各写一遍 DFS，结果是「每处都能报环，但报的内容不一样」——有的只返回布尔，有的只返回节点标识，排查时还得回去读代码。抽出最小接口后，同一份实现同时给出排序、SCC 与完整路径。

确定性落在输出边（升序）而不是容器实现上，是因为容器是实现细节：只要对外输出有序，内部用什么都行；反过来，如果只约定「用 BTreeMap」，一次重构换成别的容器就会在无提示的情况下破坏确定性。门禁检查的是「图路径上不许出现 HashMap/HashSet」，对应的是同一条原则。

最小 `Topology` 是分层的直接体现：算法在 kernel，Node 在 graph 层，两者不能互相依赖，否则内核会被迫知道领域概念。

## 反例 / 边界

- 单点上溯链不需要建图：父子层级检查直接沿 parent 链上溯，天然拿到完整路径，不需要构造整张图再跑 SCC。这类实现与「必须调 `find_cycle`」并不矛盾——约束是「给出完整路径」，不是「必须用某个函数」。
- `HashMap` 门禁只覆盖图路径：全仓禁用既无必要也无收益，其它地方仍可能出现 `HashMap`；因此它保证的是关键路径，不是全仓确定性。
- 整数槽位只存在于图视图内部：产物里的 `Def` / `Ref` 仍是字符串 id，序列化格式没有因此改变——这是已知偏差，不是遗漏。
- 节点图不是唯一消费者：`Graph` trait 还带着 UI 需要的展示数据（已拆到 `NodePresentation`）；把展示数据塞回 core trait 会让 kernel 依赖 UI 语义。

剩余缺口见 GAPS `AO-04` 段。
