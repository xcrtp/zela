# 004 · Pass 架构

> **状态**：已采纳
> **锚点**：GAPS AO-04 · AO-05 · `ze_comb::pass::PassRegistry`
> **被谁取代**：—

## 决策

求值流水线按多级 IR 组织：

```
Expr（高层 IR） → Step（低层 IR） → WGSL / C / 节点图（后端）
```

- **参照 MLIR 的 dialect + lowering，而不是 LLVM 的经典 pass manager**：我们的形态是多级 IR，不是「一个 IR 上跑一堆互相独立的改写」。
- **analysis pass 只读 IR、写 side table；transform pass 才写 IR**：`Expr` 只有 `id` 和 `node`，没有注解位——这条必须守住，否则派生量会长进 IR。
- **参考求值器本身是一个 pass**：tree-walking 的参考求值器与 lowering 后的求值器互为对拍。
- **pass 的语义变化必须显式声明**（`Semantics`），登记在 `PassRegistry` 里。

## 理由

选择多级 IR 是因为「化简」与「后端适配」是两种不同性质的工作：前者在高层做（保留结构信息），后者在低层做（丢掉结构、贴合目标）。把它们压成一个 IR 会让每一步都同时背着两套约束。

「analysis 不写 IR」是这个架构里最容易被破坏、也最值得守的一条。一旦允许在 IR 节点上挂注解，就会同时出现「IR 里的值」和「side table 里的值」两个真源；序列化格式会被迫承载派生量，产物也会随分析器实现变化而漂移。

参考求值器作为 pass 是这套架构最大的单项收益：它把「化简改变了数值路径」从人盯变成机器可测。没有它，`simplify` 这类变换的正确性只能靠抽查。

## 反例 / 边界

- **不是所有遍历都能换成访问者**：`compile_node`（lowering 派发）、参考求值器、`simplify` 的求值路径、`infer` 的类型推导这四处保留 `match`——它们有短路 `Select`、memo、词法作用域，强行改成通用遍历器会改语义。**保留是结论，不是欠账**。
- **side table 不能进产物**：一旦某个 analysis 的结果需要跨进程使用，就必须显式建模成 IR 的一部分并承担版本成本，不能「顺手序列化」。
- **`Step` 目前是最后一级**：代码生成后端未实现，所以「后端只认 Step」这条约定暂时只有一层验证；接入新后端时需要重新确认 `Step` 的信息是否足够。
- **pass 顺序是语义的一部分**：同一个 pass 集合换个顺序可能得到不同数值结果，因此顺序必须在注册表里显式固定，不能依赖遍历容器的偶然顺序。

剩余缺口见 GAPS `AO-04` 段。
