## 这篇要覆盖什么

动画横跨 6 个 crate，一篇讲清「谁拥有什么、谁每帧写什么」：

| crate | 在这条链上的位置 |
|---|---|
| [`ze-time`](../../crates/kernel/ze-time/src/lib.rs) | 时间与曲线内核：时钟树、曲线、动画值、缓动、导演 |
| [`ze-comb`](../../crates/kernel/ze-comb/src/lib.rs) | 表达式与通道：组合子 IR、编译后的程序、通道引用、求值错误 |
| [`ze-scene-core`](../../crates/scene/ze-scene-core/src/lib.rs) | 场景侧动画数据：绑定表、目标地址表、时间线、谓词分析 |
| [`ze-scene-api`](../../crates/scene/ze-scene-api/src/lib.rs) | 脚本可见面：构造器、通道常量、时钟与绑定入口、能力签名 |
| [`zela-scene-ecs`](../../crates/scene/zela-scene-ecs/src/lib.rs) | 每帧执行侧：绑定应用、以及其它按帧写组件的 System |
| [`zela-playback`](../../crates/app/zela-playback/src/lib.rs) | 装配尾与回放：时钟树 + 绑定表怎么进调度器、seek 口径 |

要回答的具体问题（现在回答不了，或回答会变）：

1. 谁每帧写什么：哪些是「值 + 时间」，哪些是「状态 + 步进」，哪些是专用通路；
2. 哪些是 `f(t)`、哪些有记忆：决定 seek 是 O(1) 还是需要重放；
3. 作者侧能不能表达：脚本里能写出来的和内部能跑的，是不是同一套；
4. 可写通道的边界：哪些字段该可动画、哪些是配置、哪些是运行时键；
5. 一条动画从脚本到像素的完整路径（含结构指纹看见/看不见什么）。

## 为什么现在留空

- 「场景侧组件与 API 专项治理」在改的正是上面这些问题：组件的分类、通道的可写面、
  脚本可见名与存储组件的对应关系。结论未定，写了就要改。
- 摸底阶段的实验有明确结局（转正 / 删除 / 待核），其中一部分是负面结论
  （某条路走不通），这些只进了 GAPS 的记账，不该先写成「机制说明」。

## 结论落地后写什么

- 一张端点表：每类动画的驱动源、写入目标、执行阶段、seek 口径；
- 一张判据表：什么样的字段可以做成通道，什么样的只能做配置；
- 一段数据流：脚本 → 装配 → 绑定 → 每帧求值 → 绘制 / 结构指纹；
- 一节反例：写错的形态会变成什么样子（没有提示；这条最有价值）。
